## 1. What this project is

**WardSentry** (repo name `CivicFix`) is a civic-grievance triage and
accountability prototype, built for hackathon problem statement PS-18
("civic grievance triage, deduplication and accountability"). Team of three,
originally built in one 12-hour session; now moving into a second,
two-day phase (see §10).

**The pitch, in one line:** citizen complaints get collapsed into real
issues, and a *recurring* issue gets linked to the public work that was
already funded to prevent it — using 60,359 real MPLADS (Member of
Parliament Local Area Development Scheme) public-works records nobody else
in the competition holds.

**What the system does, end to end:**
1. Understands each complaint (category, severity, location) from messy
   free text.
2. Collapses many complaints into one **civic issue** (deduplication).
3. Detects when a previously-closed issue **recurs**.
4. Links a recurring issue to the **public work already funded** to prevent
   it — this is the differentiator; everything else is table stakes.
5. Ranks issues by a **published formula**, never a black-box model.
6. Produces a **verification case** for a human reviewer — never a verdict
   of blame.

**Core data model rule:** ISSUE ≠ TICKET. The unit of record is the
real-world issue. A complaint (`report`) is *evidence about* an issue, not a
work item in itself — many reports collapse into one issue over time.

## 2. The central architectural idea

Two data sources are normalised independently, then joined:

| | Citizen plane | Public records plane |
|---|---|---|
| Nature | live, unstructured, multilingual | static, structured, government |
| Processing | per-complaint, synchronous | batch ETL |
| Table | `reports` → `issues` | `works` (MPLADS) |

Both reduce to the same join key before anything can correlate:

```
ward_id  ·  geo-point within radius  ·  civic category  ·  time window
```

Matching (`app/core/matcher.py`) only becomes meaningful once both sides
speak this key — hence the build order in §6 always does ingestion/NLP
before matching.

## 3. Data sources

**Runtime (used live by the app):**
- **MPLADS** — 60,359 public-work records (name, cost, status, sanction/
  completion dates, implementing agency, constituency). Already cleaned,
  in `data/mplads/MPLADS_cleaned.csv`. The primary asset; no other team in
  the competition has this.
- **PMC GIS** — Pune ward boundaries, loaded into `wards` (58 wards).
- **OSM (Overpass API)** — sensitive sites (schools, hospitals, markets,
  bus stops, water bodies) for the exposure term of the priority formula,
  cached to `data/cache/osm_sensitive_sites.json`.

**Offline / training only — never appears at runtime:**
- **NYC 311** — trains the category classifier and tuned the dedup
  similarity threshold. Kept out of `app/` deliberately (lives in
  `training/`) so training data and runtime data never blur.

**Synthetic:**
- ~400 synthetic Pune complaints, generated by `app/ingest/synthetic.py`,
  deliberately seeded near real MPLADS coordinates so issue→work links are
  genuinely findable (random coordinates would give the matcher nothing to
  match). Every synthetic row carries `is_synthetic = true` and the UI must
  label it — never presented as real citizen data (hard rule 5).

## 4. Database schema (Postgres 16 + PostGIS + pgvector)

```
wards            (id, name, geom MultiPolygon, population, area_sqkm)
reports          (id, raw_text, photo_url, reported_at, category, category_conf,
                  severity, location_phrase, geom Point, geom_confidence,
                  ward_id → wards, embedding vector(384), issue_id → issues,
                  is_synthetic)
issues           (id, category, geom Point [centroid of members], ward_id → wards,
                  first_reported, last_reported, report_count, status
                  [open|closed|reopened], closed_at, recurrence_count,
                  priority_score, priority_breakdown jsonb, embedding vector(384))
works            (id, work_name, description, cost, status, sanctioned_on,
                  completed_on, agency, constituency, category, geom Point,
                  ward_id → wards, embedding vector(384))          -- MPLADS
matches          (id, issue_id → issues, work_id → works, semantic_score,
                  distance_m, days_since_completion, combined_score,
                  match_reason text [cites both record ids], created_at)
signals          (id, issue_id → issues, match_id → matches, rule_name,
                  explanation [must name source records], source_record_ids jsonb,
                  created_at)
sensitive_sites  (id, name, kind [school|hospital|market|bus_stop|water_body],
                  geom Point)                                       -- from OSM
feedback         -- citizen confirm/dispute after an issue is marked resolved
```

`civic_category` enum (8 values): `pothole_road, drainage_sewage,
water_supply, streetlight, garbage_waste, footpath, traffic_signage, other`
— defined once in `app/categories.py`, referenced everywhere.

`severity_band` enum: `cosmetic, moderate, critical`.

GIST indexes on every `geom` column; ivfflat cosine indexes on `reports` and
`works` embeddings.

**Known gap:** `wards.population` and `wards.area_sqkm` are NULL for all 58
rows — never sourced. See §9.

## 5. Pipeline modules and the algorithms inside them

Build/dependency order: ingestion → NLP → clustering → recurrence →
matching → priority → signals → API → frontend. Matching cannot start until
both the citizen plane and the works table have geometry + embeddings.

| Module | Job | Method |
|---|---|---|
| `app/ingest/mplads.py` | load MPLADS CSV → `works` | maps work type → category, resolves location, binds ward via `ST_Contains`, batch-embeds descriptions |
| `app/ingest/wards.py` | load ward boundaries | PMC GIS geojson |
| `app/ingest/osm_sensitive_sites.py` | load exposure sites | Overpass API, cached |
| `app/ingest/synthetic.py` | generate test complaints | seeded near real MPLADS points |
| `app/nlp/classify.py` | category + confidence | sentence-transformers `all-MiniLM-L6-v2` embeddings → scikit-learn `LogisticRegression`, trained on NYC 311 mapped onto the 8 categories. Keyword-rule baseline implemented alongside for comparison. Below confidence threshold → category `other`, manual queue — never a silent guess. |
| `app/nlp/location.py` | location phrase + point | spaCy `en_core_web_sm` NER (LOC/FAC/GPE) + Pune gazetteer + regex for "near/opposite/behind X"; Nominatim geocoding with local cache. **Fallback is mandatory**: no resolved point → ward centroid, `geom_confidence = 0.4`. Never guesses a precise point. |
| `app/nlp/severity.py` | severity band | `max(category_prior, text_severity)` — category priors are a published table (e.g. open manhole ranks high regardless of wording); text severity from keyword bands. **No photo model** — photos are evidence only (hard rule 3; `photo_severity.py` exists in the repo — verify it stays evidence-only, see §9). |
| `app/core/clustering.py` | reports → issues | cosine similarity on embeddings ≥ **0.82**, Haversine distance ≤ **100 m**, reported within a **7-day** window, same category only, via DBSCAN. Deliberately conservative — two issues wrongly merged is worse than one issue wrongly split. Fuzzy-string/TF-IDF baseline implemented for comparison. |
| `app/core/recurrence.py` | reopen logic | a query, not a model: prior **closed** issues, same ward, same category, within radius. A hit reopens the issue, increments `recurrence_count`, marks the prior closure disproved. |
| `app/core/matcher.py` | issue → work link (**the differentiator**) | `cosine(issue.embedding, work.embedding)` + `ST_DWithin` spatial proximity + completion date within a plausible pre-recurrence window + same category → combined score, top-1 above threshold. Below threshold → **no match** (issue stays in the standard queue). Every match writes a human-readable `match_reason` naming both record ids. |
| `app/core/priority.py` | ranking | see formula below. Pure function of constants — never a model (hard rule 1). |
| `app/core/signals.py` | verification cases | deterministic rules only (e.g. complaint within N days of a work marked complete; repeat sanctions at the same location/category; high recurrence count with a matched work). Every `explanation` names exact source records. Language restricted to "verification signal," "anomaly signal," "evidence," "human review" — never fraud/corrupt/guilty/responsible (hard rule 6). |
| `app/nlp/translate.py`, `language.py` | multilingual intake | added post-spec (see §9) |
| `app/core/routing.py`, `metrics.py` | work-order routing; `/api/metrics` model-vs-baseline reporting | added post-spec / per §6 evaluation plan |

**Priority formula** (`app/core/priority.py`, all terms normalised 0–1,
weights are printable module-level constants, returned in a breakdown dict
so the UI can show its working):

```
Priority = 0.35·Severity + 0.25·Exposure + 0.25·Recurrence + 0.15·TimeOpen
```

```
Exposure = max{ weight(kind) : site within radius(ward_density) }
```
Site weights: school 1.0 · hospital 1.0 · market 0.7 · water_body 0.6
(raised to 1.0 for drainage/sewage-category issues) · bus_stop 0.5. `max`,
not `sum` — a pothole near five bus stops must not outrank one near a
hospital. Radius is meant to scale inversely with ward population density
(300–600m band) but currently always falls back to a flat 300m because
`wards.population`/`area_sqkm` were never populated — see §9.

## 8. Hard rules (govern every module above — never relax these silently)

1. **Priority is a formula, never a model.** Weights are constants in
   `app/core/priority.py`, printable, returned in the breakdown.
2. **Every signal names its source record ids.** No unexplained output.
3. **No photo severity model.** Photos are stored and shown as evidence
   only.
4. **Nothing hardcoded to make the demo pass.** Seeded data is fine and
   labelled. Anything presented as computed must be computed at runtime.
5. **Synthetic complaints are labelled synthetic** in schema and UI.
6. **Never imply guilt.** Permitted words: anomaly signal, verification
   priority, evidence, human review. Never: fraud, corrupt, guilty,
   responsible.
7. **Every failure degrades gracefully and says so.** Geocode fails → ward
   centroid at confidence 0.4. Match below threshold → no match.
   Classification below threshold → manual queue.

(Full text and the environment Gotchas — Postgres cluster setup, the

`CLAUDE.MD`; not duplicated here since that file is loaded automatically

## 9. Current state vs. the original spec — what's actually built, and where it drifted

22 commits in, hour-0 setup through "phase 3":

- Everything in §5–7 above is implemented and committed, not just planned.
- **Classifier is real and measured**: trained on NYC 311
  (`training/nyc311_sample.csv`), saved to
  `models/classifier_nyc311_trained.pkl`. Metrics in
  `models/classifier_metrics.json`: **macro-F1 0.929 vs. 0.385 keyword
  baseline**, 11,627 train / 2,907 test rows, all 8 categories represented.
  This is the working template for "bring a trained model to the
  hackathon" referenced in §10.
- **Built beyond the original spec's §8 "out of scope today" list**:
  `Architecture.md` explicitly excluded multilingual handling,
  confirm-before-dispatch, and a few others from the 12-hour build. Commit
  `614f722` ("Add multilingual voice intake, photo severity, work-order
  routing, and citizen feedback") and the extra API endpoints in §6 show
  the team kept building past that original scope line. **`DEMO.MD` still
  describes the narrower, original 12-hour scope and needs reconciling
  against what `app/api/main.py` and the frontend actually do now** —
  otherwise the demo script undersells (or misdescribes) the build.
- **`wards.population`/`area_sqkm` gap** (§4, §5): real, currently-inert.
  The density-scaled exposure radius code is implemented correctly but
  always falls back to flat 300m because this data was never loaded. Filling
  it would make existing code activate — no new logic needed, just data.
- **`app/nlp/photo_severity.py` exists** despite hard rule 3 ("no photo
  severity model"). Worth explicitly confirming this module only stores/
  displays photos and never feeds `severity.py` or `priority.py` before
  building further on top of it.
- **Tests**: 20 files in `tests/`, run against an isolated
  `civicfix_test` database (`TEST_DATABASE_URL`) — this isolation exists
  because a shared dev/test database once caused real MPLADS data to be
  truncated by a test fixture. Do not point `TEST_DATABASE_URL` at
  `civicfix`.

## 11. Open strategic question (raised 2026-09-24): expanding to more datasets for a two-day push

The team is moving from the completed one-day prototype into a two-day
session, considering training on additional datasets beyond MPLADS/NYC 311:
MPLADS Dashboard, PMC Open Data, Maharashtra e-Tenders, Maharashtra State
Data Bank + SDG portal, CEO Maharashtra (a longer list of municipal portals
was explicitly marked "not required now" by the user).

**Assessment, ranked by realistic payoff for two days:**
1. **PMC Open Data** — highest value, lowest risk. Structured, Pune-specific,
   could plausibly fill the ward population/area gap in §4/§5/§9, which
   would make already-written code (density-scaled exposure radius) start
   doing something instead of falling back.
2. **MPLADS Dashboard** — check for redundancy with the CSV already
   ingested before spending time here.
3. **Maharashtra e-Tender portal** — real potential (a second "money
   already spent here" signal beyond MPLADS) but ASP.NET-postback-style
   government portals are exactly the kind of scraping friction this
   project has already hit once (Nominatim rate-limiting, documented in
   `CLAUDE.MD` Gotchas). Timebox it; drop it if it fights back.
4. **State Data Bank / SDG portal / CEO Maharashtra** — lowest priority;
   nothing in WardSentry currently consumes what they'd offer.

**Resolved 2026-09-24 — phase 2 direction, confirmed by user:**
- `CLAUDE.MD`/`Architecture.md`/`BUILD_PLAN.MD` are **no longer
  authoritative scope docs** for this phase (see repo memory

- **Target for "full-fledged"**: user's words — "something that shows our

- **Runway**: ample — 3 team members, willing to push hard, explicitly
  **not willing to compromise quality "because of the formula"** i.e. don't

- **Whether phase-1's substantive hard rules (formula-not-model,
  never-imply-guilt, photo=evidence-only) still hold: user said "not sure
